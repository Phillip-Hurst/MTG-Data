# The play profile

How a single review turns into a picture of how someone plays. Two files, both in
the insights folder that `mtg_paths.resolve_output_dir` returns, alongside the
`[C] VOD Review` notes.

| File | What it is | Written how |
|---|---|---|
| `play_log.jsonl` | Append-only. One JSON object per game reviewed. Never edited, never reordered. | One line appended per game at the end of each review |
| `[C] Play Profile.md` | The rollup a human reads. Habits, strengths, pace, and what's still being watched. | Generated by `play_profile.py`. Never edited by hand |

**`play_profile.py` at the repo root does the counting.** It reads the ledger, applies
the trend bar, and rewrites the profile note. Exit codes: `0` clean, `1` couldn't run,
`2` ran and found lines it couldn't use. A hand edit to the profile note is gone on the
next run, so corrections belong in the ledger line.

```bash
python play_profile.py                 # roll up, write the profile
python play_profile.py --validate      # check the ledger, write nothing
python play_profile.py --dry-run       # print the profile, write nothing
python play_profile.py --json          # the counts, for answering a question
python play_profile.py --min-occurrences 4 --min-sessions 3   # a stricter bar
```

**Neither file ships with the plugin, and neither belongs in the repo.** They're the
user's own play data. `package.py` would drop them from a bundle anyway, and putting
them under version control would push someone's game history to a public GitHub repo.
Insights folder only.

---

## Why a ledger and not just notes

A habit claim needs a count behind it. "You're impatient with removal" is a vibe.
"You spent removal on the first legal target in 5 of the last 7 games, and in 3 of
them the real threat landed two turns later" is a finding someone can act on, and can
argue with.

Reading six review notes and remembering what they said produces the first sentence.
Counting a ledger produces the second. So every finding gets written twice: once in
prose in the review, and once as a countable row here.

## The ledger row

One object per game, not per match. A three-game match appends three lines.

```json
{
  "date": "2026-08-31",
  "source": "untapped:2f9c81a4",
  "era": "secrets-of-strixhaven",
  "your_deck": "Izzet Prowess",
  "their_deck": "Dimir Midrange",
  "game": 2,
  "result": "L",
  "on_the_play": false,
  "findings": [
    {
      "turn": 4,
      "kind": "removal-timing",
      "grade": "punt",
      "habit": "spent removal on the first legal target",
      "stated_reason": "wanted to stop the clock before it grew",
      "intent_matched_line": true,
      "prompted_by_profile": false
    }
  ],
  "pace": {
    "measure": "untapped-duration",
    "seconds_per_turn": 34,
    "tells": []
  },
  "interview": { "asked": 3, "answered": 2, "dont_remember": 1 }
}
```

### The fields that carry weight

**`kind` comes from a fixed list.** This is the whole reason the ledger works. Free
text can't be counted, and a habit spelled three ways splits into three habits, which
is the same bug the archetype alias table exists to prevent.

```
mulligan · play-draw · land-sequencing · mana-holding · trading ·
removal-timing · combat-math · sideboarding · lost-turn · rules-error
```

Adding a `kind` means adding it here first. Never invent one inline.

**`grade`** is `punt`, `close`, or `correct` (the third meaning correct and lost
anyway). Same three buckets the review uses.

**`habit`** is the one-line human description. It varies in wording, so nothing counts
on it. `kind` does the counting.

**`stated_reason`** is what the player said in the interview, quoted or close to it.
Null when they weren't asked or didn't remember.

**`intent_matched_line`** is the interesting one. True when the stated plan and the
actual play agree. False when they don't, which is its own habit worth tracking: a
player who knows the right card to play around and then makes a play that doesn't
account for it has a different problem from one who never considered the card.

**`prompted_by_profile`** is true when the finding was checked because the profile
predicted it. That flag is the confirmation-bias audit. If most findings for a habit
carry it, the habit is being found because it's expected, and the count is worth less
than it looks.

## Pace, and what can actually be measured

Think time is mostly invisible, so this section says what each source supports and
stops there. A rushing claim with no measurement behind it is a guess dressed as an
observation.

| `measure` | Source | What it gives |
|---|---|---|
| `vod-timestamps` | YouTube VOD | Real seconds per turn, per turn. The only direct measurement available |
| `untapped-duration` | untapped.gg | Game duration over turn count. One coarse average per game |
| `self-report` | The interview | "I snap-kept", "I don't remember", "I was on a timer" |
| `none` | Pasted log, screenshots | Nothing. Say so and leave `seconds_per_turn` null |

**MTGO and Arena logs carry no usable timing.** Don't derive one.

### The proxy tells

Some mistakes are the fingerprint of a fast click rather than a wrong read. They go in
`pace.tells`, from this list:

```
tapped-wrong-mana · cast-before-land-drop · missed-trigger ·
attacked-before-pump · same-15-every-matchup · sequenced-into-own-counterspell
```

**One tell is noise.** Two or more in the same game, or the same tell across games, is
a pace signal worth writing down.

**Never infer rushing from losing.** A loss is not evidence about speed. The evidence
is a timestamp, a duration, something the player said, or two tells in one game. The
review names which of those it used.

## Rolling the ledger into the profile

`play_profile.py` applies everything in this section. The rules are written out here
because they're the ones a reader needs to argue with a number, and because a value
added to the script's vocabulary and not to this note produces a `kind` the script
rejects and the skill tells Claude to write. A test fails if the two drift apart.

### The bar for calling something a trend

| Occurrences | Sessions | Where it goes |
|---|---|---|
| 3 or more | 2 or more | The profile's habit list, as a trend, with its count |
| 2 | any | The **Watching** section. Named, counted, not concluded |
| 1 | 1 | Stays in the review note. Nothing in the profile |

Two occurrences on one night is one bad night. The two-session requirement is what
separates a habit from a session.

**Every line in the profile carries its count and its date range.** A line without
one is an opinion that snuck in, and it gets deleted rather than softened.

### Strengths count too

A profile that lists only leaks is a worse tool than one that also says what someone
does well, and it's the default failure mode of every automated review. Track the good
habits to the same evidence bar: mulligan discipline, holding removal for the real
threat, boarding to what the opponent actually showed, conceding a dead game early to
save time on the clock.

A `correct` grade on a game that was lost is the raw material for this. So is a habit
that used to be a trend and has stopped appearing.

### A habit that goes quiet

Don't delete a trend that stops showing up. Move it to **Faded**, with the date of its
last appearance. Someone who fixed a leak should get to see that they fixed it, and if
it comes back the history is right there.

## The profile note

```markdown
---
author: claude
type: solution
project: MTG Tournament Analysis Skill
date: YYYY-MM-DD
tags: [mtg, vod-review, play-profile]
games_reviewed: N
range: YYYY-MM-DD to YYYY-MM-DD
---

# Play profile

**{N} games across {M} sessions, {first date} to {last date}.** Decks: {list}.

## Trends

| Habit | Kind | Count | Sessions | Grade split | Last seen |
|---|---|---|---|---|---|
| Spends removal on the first legal target | removal-timing | 5 of 7 games | 3 | 4 punt, 1 close | 2026-08-31 |

{One paragraph per trend, underneath the table. What it costs, and the one situation
where the habit is actually right, because most habits started as a correct instinct
applied too widely.}

## Strengths

{Same bar. Count and dates.}

## Pace

**Measured on {X} of {N} games.** {The numbers, the source of each, and the tells if
there are any. If pace has never been measurable, say that instead of guessing.}

## Watching

{Two occurrences. Named, counted, no conclusion drawn.}

## Faded

{Trends that stopped appearing, with the date last seen.}

## What to work on

{One thing. The same one across sessions until the ledger shows it moving.}
```

## Reading the profile without letting it write the review

The profile is read at the start of a review and written at the end, which creates an
obvious trap: read "spends removal early" first and every removal spell starts looking
early.

The order that avoids it:

1. Work the game and write the findings from what the game shows.
2. Then open the profile and check its habit list against the game.
3. Anything found only at step 2 gets `prompted_by_profile: true`.
4. A habit the profile predicted and the game doesn't support gets said out loud:
   *"Your profile says removal timing, and this game doesn't show it."*

That last one matters more than it sounds. A profile nothing can contradict stops
being a measurement.
